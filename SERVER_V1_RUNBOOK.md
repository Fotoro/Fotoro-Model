# Fotoro server v1 runbook

The v1 server runs on the owner's Linux host. The Next.js website runs on the same host. Tailscale Serve exposes the website and `/api/v1` to devices in the owner's tailnet. The Go API listens on loopback at `127.0.0.1:8765`; Next.js forwards device requests to it. Signed-in website requests resolve the owner's registered node in Supabase and forward the bearer token. Go checks that the token belongs to the locally bound owner. A paired mobile device uses a revocable, hashed device token with media-only scope. Tailscale membership is an additional network boundary, not a substitute for API authentication.

For manual on-demand operation, build with `go build -o fotoro .`, then run `./fotoroctl start`. This starts a user systemd socket without enabling boot startup. The Go API wakes on a request and exits after ten idle minutes. `./fotoroctl stop` stops both the socket and API; `./fotoroctl status` shows their state. Keep the user logged in while using the socket. For local website and desktop development, `./start-fotoro` remains available. Set `FOTORO_PRIVATE_SITE=1` when hosting the website on this machine through private Tailscale Serve.

## Configure and start

1. Install Tailscale on the Linux host and each phone. Sign them into the intended tailnet. Configure the host with `./fotoro setup` and `./fotoro nodesync` so the `nodes` row is linked to the same Supabase user who signs into the website.
2. Mount a separate secondary filesystem for backups before starting the server. Create the backup directory *on the mounted filesystem*. If the primary library is also on a removable disk, set its mount path too. Example:

   ```env
   FOTORO_STORAGE_DIR=/mnt/fotoro-primary/library
   FOTORO_PRIMARY_MOUNT_DIR=/mnt/fotoro-primary
   FOTORO_BACKUP_DIR=/mnt/fotoro-backup/library
   FOTORO_BACKUP_MOUNT_DIR=/mnt/fotoro-backup
   FOTORO_PRIVATE_SITE=1
   ```

   The primary mount variables can be omitted when the primary library is on the host's normal filesystem. The backup path and mount path must both be configured to enable verified backups. The server rejects a backup path on the primary filesystem or an unmounted backup disk. Keep the SQLite database and its `.pre-v1.snapshot` on reliable storage; the secondary media copy does not back up the database.
3. In `Fotoro-Server/site/.env.local`, configure Supabase and `FOTORO_LOCAL_SERVER_URL=http://127.0.0.1:8765`. Run `npm run build` and `npm start -- -H 127.0.0.1` to bind Next.js to loopback port 3000. Run `./fotoroctl start` on the same host. With `FOTORO_PRIVATE_SITE=1`, Go waits for the website's `/api/v1/health` and then configures Tailscale Serve for port 3000. If it times out, start the website and wake Go again, or configure `tailscale serve --bg 3000` manually.
4. Open the host's `https://<magic-dns>.ts.net` URL from a tailnet device, sign into the website as the bound owner, and pair the phone from the Devices page. The phone's device token is issued once and stored hashed on the host. Keep it in the phone's secure storage.

An earlier Funnel setup can remain public after an upgrade. Check `tailscale funnel status` and disable any old public route according to your Tailscale installation before considering the deployment private. `GET /api/v1/diagnostics` reports `tailscale.funnel_enabled` for the signed-in owner. Do not set `FOTORO_FUNNEL=1` for this private deployment.

## Upload and backup states

- The device sends a manifest to `POST /api/v1/device-assets/status`. Assets reported as `needs_upload` use resumable upload sessions. Upload chunks are limited to 16 MiB, offsets are checked, and completed originals are SHA-256 verified before they enter `media_assets`.
- The canonical timeline orders `captured_at`, falling back to `imported_at`. Image metadata and 256/1024/2048 px display copies are generated by a background worker, so the original can be acknowledged first. Originals support range reads. `./fotoro backfill-detail 25` builds at most 25 missing 2048 px copies for older photos; repeat in bounded batches when the host is idle. Originals remain unchanged. See [storage and retrieval design](STORAGE_RETRIEVAL_DESIGN.md) for the measured library and codec tradeoffs.
- When Tailscale Funnel is enabled, the authenticated media list also includes short-lived links signed by this installation for each item's small thumbnail, medium preview, available detail copy, and original. Browser image bytes go directly to the Funnel; the JSON API, pairing and uploads still require account or device authentication. A link is valid only for its media ID, size and expiry. Private deployments continue to use the authenticated website proxy.
- Storage metrics separate original media bytes, preview cache and upload staging. Disk free space comes from the primary filesystem. Run `./fotoro reconcile-sizes` once after upgrading a legacy library whose catalogue recorded zero-byte media; the server also repairs those rows in the background on startup without rewriting originals.
- The backup worker verifies legacy primary files, copies pending originals to the independent disk, and verifies secondary hashes. The website Storage page shows pending, verified, failed, missing, corrupt, and unverified counts. A phone asset is `backed_up` only after both copies are verified. `safe_to_delete` is advisory; Fotoro does not automatically delete phone originals.
- `POST /api/v1/storage/sync` runs a bounded reconciliation and copy batch. `POST /api/v1/storage/verify` checks a bounded batch of secondary copies. Both require owner authentication. The background worker also runs automatically while both disks are available.

## Checks

```bash
curl http://127.0.0.1:8765/api/v1/health
curl http://127.0.0.1:8765/api/v1/ready
tailscale serve status
tailscale funnel status
```

`/api/v1/ready` returns 503 if SQLite or the primary library is unavailable. The owner-only `/api/v1/diagnostics` includes schema version, database quick check, storage, queue, search, and Tailscale state. Before operating on an existing database, keep the automatically created `<database>.pre-v1.snapshot` and confirm `PRAGMA user_version` is 3 after migration. The initial migration creates this consistent snapshot before changing the schema.

The current implementation covers server ingestion, private routing, pairing, timeline, and verified secondary copies. A native Android background uploader, phone-side retry policy and battery/network controls, full video preview generation, database backup, and a production disaster-restore drill still need implementation and device-level verification.
